<KeyPoints>
- A **version control system (VCS)** manages changes to documents and their versions. Every version (revision) has a **timestamp, an author, and a description**.
- Four use cases: **history**, **working with others**, **branching**, **external contributors** (forks).
- **Centralised VCS** (SVN, CVS): history lives only on the server; without a connection you cannot go back. **Distributed** (Git): **the whole history is on your machine too**, and most operations work offline.
- Git stores **snapshots** of the whole project; an unchanged file is not stored again, just referenced.
- Store files that were **not generated by a tool** (sources, scripts, docs, images). Build output (`.o`, `.exe`, `.class`…) does **not** belong there.
</KeyPoints>

## The problem without version control

Without a tool, a project's history looks like this:

```text
thesis.docx
thesis_final.docx
thesis_final2.docx
thesis_final_really.docx
thesis_final_really_fixed.docx
```

You cannot tell which version is the latest, who changed it, what changed between versions, or why. It is easy to overwrite or delete an older version by mistake.

## What is version control

**Version control** (also called *revision control*) keeps track of changes to documents, programs, websites, and other files. Think of a project as a **timeline of snapshots** of every version:

- each change gets an identifier (revision 1, 2, 3… — in Git, the commit hash),
- every revision records **when** and **who**,
- revisions can be **compared**, **restored**, and some can be **merged**.

### Four use cases

| Use case | What a VCS gives you |
| --- | --- |
| **1. History** | Go back to any earlier version. See **when, who, what, and why**. Deleted content stays in the history. When something breaks, you can find the change that caused it. |
| **2. Working with others** | Share files with the team without USB sticks, e-mail, or a shared drive. Colleagues' changes are merged and nothing is accidentally overwritten. |
| **3. Branching** | Several variants of the same software at once: main, maintenance (fixes for older releases), development (disruptive changes), release (freezing code before a release). |
| **4. External contributors** | Open source: anyone can **fork** the project (make their own copy), fix something there, and send the change back for approval. |

## Centralised vs. distributed VCS

| | Centralised (Subversion, CVS) | Distributed (Git, Mercurial) |
| --- | --- | --- |
| Where the history is | only on the **central server** | **on everyone's machine** — a local repo is a full copy |
| Getting the project | *checkout* of the current state | *clone* of the whole history |
| Commit | straight to the server (*check in*) | into the **local** repo, to the server later with *push* |
| Offline | almost nothing — older versions come from the server | commit, history, diff, branches all work without a network |
| Speed | every operation goes over the network | most operations are local, so fast |

In a centralised system you only have the current files and your changes are not versioned until you send them to the server. In Git you commit locally and, when ready, send the commits to the server with **push**; you get other people's changes with **pull**.

## Git stores snapshots

Centralised systems remember the **differences** of each file. Git remembers a **snapshot of the whole project** at every commit:

```text
Version 1:  login(A)   signup(B)   home(C)
Version 2:  login(A1)  signup(B)   home(C1)    ← B unchanged, reference to B from version 1
Version 3:  login(A1)  signup(B)   home(C2)    ← only C changed
```

An unchanged file is not stored twice — the snapshot just points to it. That is why switching versions and branches in Git is so fast.

## What belongs in a repository

A **repository** is a project in Git together with its whole history.

| Store | Do not store |
| --- | --- |
| source files (`.c`, `.java`, `.py`, `.tex`…) | build output: `.o`, `.a`, `.so`, `.dll`, `.class`, `.jar`, `.exe` |
| build scripts and project files (`Makefile`, `CMakeLists.txt`, `.sln`) | generated documents: `.dvi`, `.ps`, `.pdf` from LaTeX |
| documentation (`README.md`, `.txt`) | sources and scripts generated by a tool (autoconf, cmake, lex, yacc) |
| resources: images, audio, static assets | |

Why not generated files? A colleague can build the project themselves. If you both committed binaries, you would get **needless conflicts** — and binary files can be neither merged nor read sensibly. To ignore them, use [.gitignore](/devops-notes/en/git/gitignore/).

:::note[Large files]
Git handles ordinary images fine. Very large files (videos, datasets) are handled differently — for example with the Git LFS extension. That is outside this course.
:::

## Test yourself

<Question q="What is stored with every revision?">
The snapshot of the files, the **time** of the change, the **author**, and a description (the commit message). Revisions can be compared and restored.
</Question>

<Question q="What is the main difference between a centralised and a distributed VCS?">
In a centralised one the history lives only on the server — without a connection you cannot get an older version or commit. In a distributed one (Git) everyone has a **full copy of the history**; commit, diff, and log work offline, and changes go to the server with `push`.
</Question>

<Question q="Why is switching versions in Git fast?">
Git stores snapshots of the whole project but does not store unchanged files again — the snapshot points to their latest version. Everything is also local, so nothing has to be downloaded.
</Question>

<Question q="Why not put `.o` or `.exe` files in the repository?">
The compiler generates them — everyone can build them from the sources. Committing them causes needless conflicts that cannot be resolved sensibly for binary files.
</Question>

<Question q="What is a fork?">
A copy of someone else's repository under your account. You change it and send the maintainer of the original project a request (pull/merge request) to take the change.
</Question>

## Exercises

### 1.1 · Manual file versions

Create a folder `no-git` with `plan.txt` describing a small app. Then make three copies named `plan-final.txt`, `plan-final2.txt`, and `plan-fixed.txt`, with a small change in each. Work out which is the newest and what changed in it. Why would this be a problem in a real project?

<p class="practises">Practises: the motivation for version control.</p>

<Solution>
The order of versions cannot be reliably told from the names (is `fixed` newer than `final2`?). There is no timestamp, author, reason, or reliable diff — you have to spot the differences by eye. Git solves this with commits: each stores the project state with metadata, and `git diff` / `git log` show exactly what changed, who changed it, and when.
</Solution>

### 1.2 · Store it or not?

For each file of a Java project, decide whether it belongs in the repository: `Main.java`, `Main.class`, `pom.xml`, `README.md`, `target/app.jar`, `logo.png`, `debug.log`.

<p class="practises">Practises: what belongs in a repository.</p>

<Solution>
Yes: `Main.java` (source), `pom.xml` (build script), `README.md` (docs), `logo.png` (resource). No: `Main.class` and `target/app.jar` (build output), `debug.log` (generated by the running app).
</Solution>
