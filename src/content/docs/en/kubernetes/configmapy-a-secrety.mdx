<KeyPoints>
- Configuration written straight into a manifest ends up in Git. Like `.env` files in Docker, here there are ConfigMaps and Secrets — both store **key-value** pairs in **etcd**.
- **ConfigMap** = non-sensitive data (`describe` shows the values). **Secret** = sensitive data (`describe` shows only the number of bytes).
- Creating: `--from-literal KEY=value` or `--from-env-file file.env`. Using: one key via `valueFrom` (`configMapKeyRef` / `secretKeyRef`), the whole object via `envFrom` (`configMapRef` / `secretRef`) — then the **keys must be named like the application's variables**.
- `env` takes precedence over `envFrom`. Values are read **when the pod is created** — changing or deleting a ConfigMap doesn't affect running pods. A pod referring to a non-existent ConfigMap stays in `CreateContainerConfigError`.
- A Secret is just **base64**, not encryption: `echo -n 'x' | base64` and back with `base64 --decode`. Real secrecy needs external tools.
</KeyPoints>

## Why

So far the configuration is part of the application — the database and WordPress manifests contain environment variables, passwords included. In Docker we solved this with `.env` files, because we don't want:

- to type lots of variables by hand on every run,
- sensitive data publicly in **Git** — anyone with access to the repository would see the logins and passwords.

Kubernetes has two objects for this:

| | ConfigMap | Secret |
| --- | --- | --- |
| for | non-sensitive configuration (units, city, interval…) | sensitive data (passwords, tokens, API keys, certificates) |
| `describe` | shows keys **and values** | shows only keys and the **number of bytes** |
| storage | etcd | etcd, values in base64 |

Both can be created imperatively (`kubectl create`) and declaratively (a manifest). Pods access them through **environment variables** or as **files in a volume**. Since they're in etcd, they can be shared across the cluster.

The demo uses the **weather** app — its variables are listed on its Docker Hub page:

- into the ConfigMap: `WEATHER_UNITS`, `WEATHER_QUERY`, `WEATHER_UPDATE_INTERVAL`,
- into the Secret: `WEATHER_TOKEN` (the OpenWeatherMap API key).

## ConfigMap

### Creating

```bash
kubectl create configmap weather \
  --from-literal WEATHER_UNITS=metric \
  --from-literal WEATHER_QUERY=poprad,sk \
  --from-literal WEATHER_UPDATE_INTERVAL=30
```

```bash
kubectl get configmaps                # short cm; get all doesn't show them
# NAME               DATA   AGE
# kube-root-ca.crt   1      9d
# weather            3      5s
kubectl describe configmap weather    # keys and values
```

`DATA` is the number of keys. `kube-root-ca.crt` is a certificate Kubernetes adds to every namespace.

### One key: valueFrom

```yaml
    spec:
      containers:
      - image: bletvaska/weather
        name: weather
        env:
        - name: WEATHER_QUERY          # the variable in the container
          valueFrom:
            configMapKeyRef:
              name: weather            # the ConfigMap's name
              key: WEATHER_QUERY       # the key in it
```

"Take the value of the `WEATHER_QUERY` key from the `weather` ConfigMap and put it into the variable `WEATHER_QUERY`." Here the key and the variable **needn't have the same name** — you map them by hand. But it's four extra lines per key.

### The whole ConfigMap: envFrom

```yaml
      containers:
      - image: bletvaska/weather
        name: weather
        envFrom:
        - configMapRef:
            name: weather
```

All the ConfigMap's keys become environment variables. Here the **keys must be named exactly like the variables the application expects** (case included) — otherwise they'll be in the container but the application won't use them and falls back to its default (Košice for weather). `envFrom` is a list, so you can load several ConfigMaps and Secrets.

### Checking

```bash
kubectl apply -f weather.yaml
kubectl exec -it deployment/weather -- printenv | grep WEATHER
kubectl logs deployment/weather           # the weather for Poprad
kubectl describe pod -l app=weather       # the Environment section
```

### Precedence

When the same variable is in `env` and in a ConfigMap via `envFrom`, **`env` wins** — as in Docker, where a manual `-e` wins over `--env-file`. In class we put `WEATHER_QUERY=ruzomberok,sk` in `env` and the pod had Ružomberok, not Poprad. The order of keys in the manifest doesn't matter. If the same key is in **several** ConfigMaps in `envFrom`, the order decides — but that's a configuration mistake.

### From a .env file

```bash title="weather.env"
WEATHER_UNITS=metric
WEATHER_QUERY=poprad,sk
WEATHER_UPDATE_INTERVAL=30
```

```bash
kubectl create configmap weather --from-env-file weather.env
```

The file can have comments, and you can turn it into a template with a sample configuration that may go into Git.

### As a manifest

```bash
kubectl create configmap weather --from-env-file weather.env \
  --dry-run=client --output yaml > weather.cm.yaml
kubectl get configmap weather --output yaml        # from an existing one
```

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: weather
data:
  WEATHER_QUERY: poprad,sk
  WEATHER_UNITS: metric
  WEATHER_UPDATE_INTERVAL: "30"
```

Numbers are quoted — ConfigMap values are always strings. Put it in the application's manifest **before** the deployment, so it exists when the pods are created.

### Deleting and a missing ConfigMap

```bash
kubectl delete configmap weather
```

**Nothing** happens to running pods — a ConfigMap is used only when a pod is **created**. The trouble comes when a new pod is created (restart, scaling, deleting a pod):

```bash
kubectl get pods
# weather-…   0/1   CreateContainerConfigError   0   10s
kubectl describe pod -l app=weather
# Warning  Failed  …  Error: configmap "weather" not found
```

Kubernetes retries at regular intervals; once you create the ConfigMap, the pod starts. The deployment itself is created even without the ConfigMap — its definition is correct, only the resource is missing.

### Changing it on the fly

A change of values in a ConfigMap shows up only in **new** pods. Running ones need restarting — delete the pods, scale the deployment to 0 and back, or delete and re-apply the manifest. Kubernetes doesn't restart pods on a ConfigMap change by itself (there are extensions for that).

:::tip[Restarting a deployment]
A neater way, not shown in class: `kubectl rollout restart deployment/weather` — it replaces the pods gradually, as in a rolling update.
:::

## Secret

### Creating

```bash
kubectl create secret generic weather \
  --from-literal WEATHER_TOKEN=<API_KEY>
kubectl create secret generic weather --from-env-file credentials.env
```

`generic` is the common type (`Opaque`). A Secret can also store certificates (type `tls`) or registry credentials.

```bash
kubectl get secrets
# NAME      TYPE     DATA   AGE
# weather   Opaque   1      5s
kubectl describe secret weather
# Data
# ====
# WEATHER_TOKEN:  32 bytes
```

You don't see the value — only its length.

### Using it

```yaml
        env:
        - name: WEATHER_TOKEN
          valueFrom:
            secretKeyRef:
              name: weather
              key: WEATHER_TOKEN
```

or the whole Secret:

```yaml
        envFrom:
        - configMapRef:
            name: weather          # the weather ConfigMap
        - secretRef:
            name: weather          # the weather Secret — a different object type, the same name is fine
```

In the container the value is **decoded** — the application gets the original token. After applying, the browser finally shows the weather.

### base64 isn't encryption

```bash
kubectl get secret weather -o yaml
# data:
#   WEATHER_TOKEN: PEFQSV9LRVk+
```

```bash
echo -n 'janosik' | base64              # amFub3Npaw==
echo -n 'amFub3Npaw==' | base64 --decode   # janosik
```

Secret values are only encoded with **base64**, which anyone can decode. Whoever can read a Secret sees the password too. When writing a manifest by hand, you have to base64-encode the values yourself (`echo -n`, so the newline isn't encoded too).

Real secrecy uses external stores and extensions — e.g. *External Secrets Operator* or [gopass](https://github.com/gopasspw/gopass) (Krew has `kubectl gopass`). Which one is the team's decision.

## One object for everyone?

In class someone suggested one ConfigMap and one Secret `wordpress` for both WordPress and MariaDB. It works, but it **isn't secure** — each container would have the credentials of the other application in its variables too, so hacking one gives you the whole infrastructure. Each application gets its own objects.

## Test yourself

<Question q="When do you use a ConfigMap and when a Secret?">
A ConfigMap for non-sensitive configuration, a Secret for passwords, tokens, and keys.
</Question>

<Question q="What is the difference between `valueFrom` and `envFrom`?">
`valueFrom` maps one key to one variable (the names may differ). `envFrom` loads all keys as variables — key names must match the application's variables.
</Question>

<Question q="A variable is in `env` and also in a ConfigMap via `envFrom`. Which wins?">
The value from `env`.
</Question>

<Question q="You deleted a ConfigMap. What happens to running pods, and to new ones?">
Running ones are unaffected — they got the values at creation. New pods stay in `CreateContainerConfigError` until you recreate the ConfigMap.
</Question>

<Question q="You changed a value in a ConfigMap. When does the application see it?">
Only in new pods — running ones need restarting.
</Question>

<Question q="Is a Secret encrypted in Kubernetes?">
No, the values are only base64. Whoever can read the Secret can read the value.
</Question>

<Question q="Why not put the credentials of WordPress and the database in one Secret?">
Each container would see credentials it doesn't need — compromising one application would reveal all of them.
</Question>

## Exercises

### 12.1 · RustFS with a ConfigMap and a Secret

A manifest for [RustFS](https://hub.docker.com/r/rustfs/rustfs):

- namespace `prod`, image `rustfs/rustfs`, one instance,
- ports 9000 (S3 API) and 9001 (console) exposed,
- admin `janosik` with password `valaska123` (`RUSTFS_ACCESS_KEY`, `RUSTFS_SECRET_KEY`),
- time zone `TZ=Europe/Bratislava`,
- memory from 128Mi to 512Mi, CPU from 100m to 500m.

Handle the variables with a ConfigMap and a Secret.

<p class="practises">Practises: ConfigMap and Secret as a manifest, `envFrom`, several ports in a service.</p>

<Solution>
```yaml title="rustfs.yaml"
apiVersion: v1
kind: Namespace
metadata:
  name: prod
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: rustfs-config
  namespace: prod
data:
  TZ: Europe/Bratislava
---
apiVersion: v1
kind: Secret
metadata:
  name: rustfs-secret
  namespace: prod
data:
  RUSTFS_ACCESS_KEY: amFub3Npaw==        # janosik
  RUSTFS_SECRET_KEY: dmFsYXNrYTEyMw==    # valaska123
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rustfs
  namespace: prod
  labels:
    app: rustfs
spec:
  replicas: 1
  selector:
    matchLabels:
      app: rustfs
  template:
    metadata:
      labels:
        app: rustfs
    spec:
      containers:
      - image: rustfs/rustfs
        name: rustfs
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 512Mi
        envFrom:
        - configMapRef:
            name: rustfs-config
        - secretRef:
            name: rustfs-secret
---
apiVersion: v1
kind: Service
metadata:
  name: rustfs
  namespace: prod
  labels:
    app: rustfs
spec:
  type: LoadBalancer
  selector:
    app: rustfs
  ports:
  - name: s3
    port: 9000
    protocol: TCP
    targetPort: 9000
  - name: console
    port: 9001
    protocol: TCP
    targetPort: 9001
```

```bash
kubectl apply -f rustfs.yaml
kubectl exec -n prod deployment/rustfs -- date     # Central European time (CET/CEST)
# http://<IP>:9001 → janosik / valaska123
```

`TZ` changes only the system time in the container (`date`). The time the web console shows next to buckets is up to the application. Without `TZ`, `date` would show UTC.
</Solution>

### 12.2 · WordPress — security first

Change the [WordPress](/devops-notes/en/kubernetes/wordpress/) manifest so that no password is directly in a deployment. Each application gets its own ConfigMap and its own Secret.

<p class="practises">Practises: splitting configuration, base64, `envFrom`.</p>

<Solution>
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: wordpress
  namespace: wordpress
data:
  WORDPRESS_DB_HOST: db:3306
  WORDPRESS_DB_NAME: wordpress
---
apiVersion: v1
kind: Secret
metadata:
  name: wordpress
  namespace: wordpress
data:
  WORDPRESS_DB_USER: d3B1c2Vy              # wpuser
  WORDPRESS_DB_PASSWORD: ZW5kMzIx          # end321
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: mariadb
  namespace: wordpress
data:
  MARIADB_DATABASE: wordpress
---
apiVersion: v1
kind: Secret
metadata:
  name: mariadb
  namespace: wordpress
data:
  MARIADB_ROOT_PASSWORD: dG9wLnNlY3JldA==  # top.secret
  MARIADB_USER: d3B1c2Vy
  MARIADB_PASSWORD: ZW5kMzIx
```

In the deployments replace `env` with:

```yaml
        envFrom:                 # db
        - configMapRef:
            name: mariadb
        - secretRef:
            name: mariadb
```

```yaml
        envFrom:                 # app
        - configMapRef:
            name: wordpress
        - secretRef:
            name: wordpress
```

In class a name got mixed up once and WordPress received the `mariadb` ConfigMap and Secret — check with `kubectl exec … -- printenv`.
</Solution>
