<KeyPoints>
- **Dynamic Task Mapping** creates **at run time** one task instance per item of a list. You do not need 10 (or 800) identical DAGs that differ only in a parameter.
- A DAG parameter as a list: `@dag(params={"query": Param(default=[...], type="array", title=..., description=...)})` — in the Trigger form it is a “one item per line” field.
- The Variable with cities (one per line) is a string — turn it into a list with `.split()`.
- A run's parameters are in the **context**, which you get only inside a task: `get_current_context()["params"]["query"]`.
- `.expand(query=locations)` — one instance per item; `.partial(units="metric")` — the same value for every instance.
- Map the **whole group**: `tg_weather_ingestion.expand(query=locations)`. One city's error then stops only its own branch; with `AirflowSkipException` the run even ends successfully.
</KeyPoints>

## The problem

The DAG downloads the weather for one city. We want **several** — and for each city separately: download, validate, process, and publish. A separate DAG per city makes no sense: at the university where Mirek teaches, Airflow is being prepared to grade student assignments — a DAG for one student is simple, but there are 800+ students.

The answer is **Dynamic Task Mapping**: the DAG stays one, and at run time Airflow creates as many task instances as there are items in the list.

Two things need solving:

1. how to give a **list** of places — in the Variable and by hand when triggering,
2. how to feed the cities to a task **one at a time**.

## A DAG parameter: Param

So far `query` was a plain string (`query: str = …`). In the Trigger form that is a single-line field — you cannot type Enter there. The **`Param`** type from `airflow.sdk` describes a parameter in more detail:

```python
from airflow.sdk import Param

Param(
    default=[],
    type="array",                 # Airflow types, as strings — not Python types
    title="Locations",
    description="List of locations. One location per line.",
)
```

| Property | Meaning |
| --- | --- |
| `type` | the value's type as a string: `"string"`, `"integer"`, `"number"`, `"boolean"`, `"array"`, `"object"` (as in [JSON Schema](/devops-notes/en/python-advanced/validacia-dat/)) |
| `default` | the default value |
| `title` | the field's heading in the Trigger form |
| `description` | the description under the field |

### Where it goes: `params=` in the decorator

The instructor first used it as the default value of a function parameter: `def main(query=Param(...))`. Ruff underlined it (*Do not perform function call `Param` in argument defaults* — rule B008), and with several parameters the function header would be huge — each takes 5 lines. So they belong in the **`params`** dictionary of `@dag`:

```python
@dag(
    "weather_scraper",
    ...,
    params={
        "query": Param(
            default=Variable.get("weather_city", default="kosice,sk").split(),
            type="array",
            title="Locations",
            description="List of locations. One location per line.",
        ),
    },
)
def main():
    ...
```

### Cities from the Variable: `.split()`

The `weather_city` Variable has the cities on separate lines — it is a **string** with `\n`. Given as the `default` of an `array` parameter, Airflow rejects it:

```text
ParamValidationError: 'kosice,sk\npresov,sk' is not of type 'array'
```

The string has to be split into a list with the **`split()`** method. Without an argument it splits on **whitespace** (space, tab, newline); with one, on the given separator (`"a,b".split(",")`):

```python
>>> "ruzomberok,sk\nkosice,sk\npresov,sk".split()
['ruzomberok,sk', 'kosice,sk', 'presov,sk']
```

The Trigger form then shows a field with the list of places from the Variable — scheduled runs use it as it is; on a manual run you can overwrite it (e.g. just one city, to test).

:::tip[When the form shows only the first city]
For one participant the form showed only the first city. The code and the Variable were fine — old unfinished runs were hanging in Airflow. `sudo systemctl restart airflow` and refreshing the page helped.
:::

## The run context

How do you get at the parameter? The `main()` function runs when the DAG is **parsed** — no run exists yet then. The values belong to a specific run and live in the **context**.

**Context** is a term you meet in applications everywhere: something like global data reachable from any part of the application. In Airflow every DAG run (and every task) has its own context — when the run was created, which DAG, which parameters, the task instance… You get it **only inside a task**, with `get_current_context()`:

```python
from pprint import pprint

from airflow.sdk import get_current_context, task


@task(task_display_name="Get Locations")
def get_locations() -> list[str]:
    context = get_current_context()
    pprint(context)                       # let us see what is inside
    return context["params"]["query"]
```

The context is a dictionary (in Airflow 3.3 with keys such as `dag`, `dag_run`, `run_id`, `logical_date`, `params`, `task`, `ti` / `task_instance`, `triggering_asset_events`…). `print()` prints it as one long line; `pprint` (*pretty print*) prints it readably. `params` is a dictionary inside the dictionary, hence `context["params"]["query"]`.

:::caution[`-> dict` is not just a note]
The instructor first wrote `def get_locations() -> dict:`, and the task failed: *Returned output was type &lt;class 'list'&gt; expected dictionary for multiple_outputs*. When a task's return type is `dict`, Airflow infers `multiple_outputs=True` — it splits the dictionary into separate XCom values and requires a dictionary. The task returns a list, so the right annotation is `-> list[str]`.
:::

## .expand() and .partial()

If you pass the result of `get_locations()` (a list) straight into `scrape_data(locations)`, the task does not crash — but it runs **once** for the whole list. httpx turns it into a repeated parameter `?q=ruzomberok,sk&q=kosice,sk&…`, and OpenWeatherMap takes only the first city. We want one instance per city.

| Method | Meaning |
| --- | --- |
| `.expand(arg=list)` | the argument the task is multiplied by — each item of the list is put into `arg` in turn |
| `.partial(arg=value)` | arguments that are **the same** for every instance |

```python
locations = get_locations()
data = scrape_data.expand(query=locations)   # query: str ← one city at a time
valid_data = validate_data.expand(payload=data)
```

- `query` is a string (one city), `locations` is a list. `expand` “unpacks” the list and for each item runs one instance with `query` = that city.
- A mapped task's result is a list again, so the next task is mapped with `.expand(...)` too.
- In the graph a mapped task has **square brackets** with the number of instances after its name. The *Mapped Tasks* tab numbers the instances (*map index* 0, 1, 2…) in list order. Which city is which you find in an instance's detail under *Rendered Template*.

**`.partial()`** — if `scrape_data` also had a `units` parameter, the same for every city:

```python
scrape_data.partial(units="metric").expand(query=locations)
# scrape_data(query="kosice,sk", units="metric"), scrape_data(query="presov,sk", units="metric"), …
```

## When one city fails

The instructor added a non-existent city `xxxx` to the list. OpenWeatherMap returned 404, its `scrape_data` failed — and **all** instances of `validate_data` and the rest were `upstream_failed`. Not even the cities that downloaded fine were processed.

Why: when chaining `scrape_data.expand(...)` → `validate_data.expand(...)`, the mapped `validate_data` depends on the **whole** mapped `scrape_data`. One instance fails → the dependency fails for all.

### The fix: a mapped task group

Instead of individual tasks, map the **whole group** — each city gets its own branch `scrape → validate → process → publish`:

```python
@task_group(group_display_name="Weather Ingestion")
def tg_weather_ingestion(query: str):
    data = scrape_data(query)          # inside the group: ordinary calls, no expand
    valid_data = validate_data(data)
    line = process_data(valid_data)
    publish_data(line)


@dag(...)
def main():
    locations = tg_healthcheck() >> get_locations()
    tg_weather_ingestion.expand(query=locations)
```

<Pipeline steps={[{ group: 'Healthcheck', steps: ['ping', 'openweathermap', 'rustfs'] }, 'get_locations', { group: 'Weather Ingestion [N]', steps: ['scrape → validate → process → publish'] }]} caption="The group is mapped N times — one branch per city." />

Verified on Airflow 3.3.2 with the list `kosice, xxx, presov`:

| Variant | Cities processed | DAG run |
| --- | --- | --- |
| `scrape.expand` → `validate.expand` → `publish.expand` | **none** | `failed` |
| `tg.expand(...)`, unknown city → `AirflowFailException` | Košice, Prešov | `failed` |
| `tg.expand(...)`, unknown city → **`AirflowSkipException`** | Košice, Prešov | `success` |

### Skipping: AirflowSkipException

`AirflowFailException` is a universal “it crashed”. Special exceptions have special behaviour: **`AirflowSkipException`** marks the task as **`skipped`** (pink), and the tasks after it in the branch are skipped too. The instructor uses it when grading assignments — a student who made no change to their code is skipped. Out of 800 students, 200 remain with a change, some of those fail to compile, and only the rest are graded.

```python
from airflow.sdk.exceptions import AirflowSkipException

if response.status_code == HTTPStatus.NOT_FOUND:
    logger.warning("Unknown city %s, skipping", query)
    raise AirflowSkipException(f"City {query} not found.")
```

In the course the instructor did not get this working in time (he also tried `trigger_rule="all_done"`); with a mapped group it works as shown in the table above. Whether an unknown city is an error (`failed`) or just “nothing to do” (`skipped`) is a design decision.

:::caution[Several instances write to one file]
All branches append to the same `dataset.csv` in S3 (“download → append → upload”). If two `publish_data` instances ran at the same time, one would overwrite the other's write. In the course it did not matter (low `parallelism`), but it is safer to limit concurrency: `@task(..., max_active_tis_per_dagrun=1)` — within one run, at most one `publish_data` instance runs at a time. The alternative is a separate file per city (`kosice-sk.csv`).
:::

Another consequence: `publish_data` has `outlets=[WEATHER_DATA]` and now runs once per city — **each** successful instance creates an asset event. In the test, `report_builder` ran twice for a run with two cities.

## The whole DAG

The resulting `weather_scraper.py` (with the notifications from the next chapter) is in the [Midnight report](/devops-notes/en/python-advanced/polnocny-report/#the-whole-project-after-day-5) chapter. The essential parts:

```python
@task(task_display_name="Get Locations")
def get_locations() -> list[str]:
    """Cities for this run — from the Trigger form, or the default from the Variable."""
    context = get_current_context()
    return context["params"]["query"]


@task_group(
    group_display_name="Weather Ingestion",
    tooltip="Retrieve, process and upload weather info.",
)
def tg_weather_ingestion(query: str):
    data = scrape_data(query)
    valid_data = validate_data(data)
    notify(valid_data)
    line = process_data(valid_data)
    publish_data(line)


@dag(
    "weather_scraper",
    ...,
    params={
        "query": Param(
            default=Variable.get("weather_city", default="kosice,sk").split(),
            type="array",
            title="Locations",
            description="List of locations. One location per line.",
        ),
    },
)
def main():
    locations = tg_healthcheck() >> get_locations()
    tg_weather_ingestion.expand(query=locations)
```

## Test yourself

<Question q="What is Dynamic Task Mapping, and what problem does it solve?">
At run time it creates one instance of a task (or group) for each item of a list. You do not need a separate DAG per city or student — there is one DAG and only the input changes.
</Question>

<Question q='Why does a `Param` of type `"array"` with the default `Variable.get("weather_city")` fail, and how do you fix it?'>
The Variable is a string with cities on lines, not a list: *is not of type 'array'*. You need `Variable.get(...).split()`.
</Question>

<Question q="Why do DAG parameters belong in `params=` of `@dag` and not in the header of `main()`?">
Calling a function in a parameter's default value is a bad habit (Ruff B008), and with several parameters the header would be huge. `params` is a dictionary — readable and standard in Airflow.
</Question>

<Question q="How does a task get the `query` parameter from the Trigger form?">
`get_current_context()["params"]["query"]` — the context is available only while a task runs.
</Question>

<Question q="Why does a task annotated `-> dict` that returns a list fail?">
With a `dict` return type Airflow sets `multiple_outputs=True` and expects a dictionary.
</Question>

<Question q="What is the difference between `.expand()` and `.partial()`?">
`.expand()` puts each item of a list into an argument in turn (one instance per item). `.partial()` sets an argument that is the same for every instance.
</Question>

<Question q="Why, when chaining `scrape.expand()` → `validate.expand()`, does one bad city stop them all?">
The mapped `validate` depends on the whole mapped `scrape`; when one instance fails, all `validate` instances are `upstream_failed`. The fix is to map the whole group (`tg.expand(...)`) — each city gets its own branch.
</Question>

<Question q="What is the difference between `AirflowFailException` and `AirflowSkipException` in a mapped group?">
With `AirflowFailException` the other cities are processed, but the run ends `failed`. With `AirflowSkipException` the branch is marked `skipped`, the other cities are processed, and the run ends `success`.
</Question>

## Exercises

### 19.1 · Cities without duplicates

Change `get_locations()` to strip spaces around names, lower-case them, and drop empty items and duplicates (keeping the order).

<Solution>
```python
@task(task_display_name="Get Locations")
def get_locations() -> list[str]:
    locations = get_current_context()["params"]["query"]
    cleaned = (location.strip().lower() for location in locations)
    return list(dict.fromkeys(location for location in cleaned if location))
```

`dict.fromkeys()` keeps the order of first occurrence and drops duplicates (dictionary keys are unique).
</Solution>

### 19.2 · Skip an unknown city

Change `scrape_data` so that on 404 it logs a WARNING and **skips** that city's branch (the run should end successfully); on other errors it should fail.

<Solution>
```python
from airflow.sdk.exceptions import AirflowFailException, AirflowSkipException


@task(task_display_name="Scrape Data")
def scrape_data(query: str) -> dict:
    ...
    response = httpx.get(url, params=params, timeout=10)
    if response.status_code == HTTPStatus.NOT_FOUND:
        logger.warning("Unknown city %s, skipping", query)
        raise AirflowSkipException(f"City {query} not found.")
    if response.status_code != HTTPStatus.OK:
        raise AirflowFailException(f"Cannot get weather for {query}: {response.text}")
    return response.json()
```

It works thanks to the mapped group: only the unknown city's branch is skipped.
</Solution>
