## PyCharm is the best IDE…

> “PyCharm is the best environment you can use, which is why we will not use it.”

The course uses **VS Code** throughout — because we work on a remote server over SSH and everyone gets the same setup.

<p class="wisdom-day">Day 1</p>

## Ruff pushed out Black

Until recently **Black** was the most popular formatter; **Ruff** has taken the lead — it is a formatter **and** a linter in one. It is written in Rust, so it is many times faster than Black or Flake8. In VS Code you also need to install it as an extension — otherwise *Format Document* reports that no formatter is installed.

<p class="wisdom-day">Day 1</p>

## ipython — a “much sexier” interpreter

Instead of the plain `python` REPL, use **ipython**: colours, history, and above all `object.` + `Tab` lists every attribute and method, and `variable?` shows its type and documentation. The fastest way to explore an unfamiliar object (such as an HTTP response).

According to Mirek this is Python's strength: in Java it is always *edit → compile → run → look*. In Python you polish the code live in ipython, and once you are happy you copy it into the file and test it once.

<p class="wisdom-day">Day 1</p>

## f-strings: THIS IS THE WAY

Do not join strings with `+` — “at most if there are two strings, and even then, reflect on yourself”. With longer text (say, a web page) you would be moving the cursor around looking for where to split and where to join — “you will go grey”. Use an f-string: `f"{url}?q={query}"`.

<p class="wisdom-day">Day 1</p>

## “This will never happen”

The worst code you can come across:

```python
except Exception as ex:
    # this will never happen
    pass
```

Handle every caught exception — at least log it with `logging.exception()`.

<p class="wisdom-day">Day 1</p>

## No Bulgarian constants

Unexplained numbers (`if status == 404`) are “Bulgarian constants”. Name them: `HTTPStatus.NOT_FOUND`, your own constants in `UPPER_CASE`.

<p class="wisdom-day">Day 1</p>

## Put everything in a function

Even the workflow's sequence of steps belongs in `main()`, started via `if __name__ == "__main__":`. And DRY — repeated logic belongs in a function. (But mind WET too: wait with the abstraction until the code repeats 2–3 times.)

<p class="wisdom-day">Day 1</p>

## Secrets in environment variables

Anyone can see an API key passed as an argument with `ps aux`. An environment variable does not show up in the process list — “an environment variable is not a process”.

```bash
APPID=<API_KEY> ./workflow.py kosice
```

<p class="wisdom-day">Day 1</p>

## pendulum instead of datetime, dates in ISO 8601

`datetime` is not comfortable to work with, especially time zones — **pendulum** is backwards compatible and nicer. And write dates in ISO 8601 (`2026-05-19T13:07:18Z`), not the European way or with the “American logic” of `MM/DD/YYYY`.

<p class="wisdom-day">Day 1</p>

## Store time in UTC

Always store and calculate times in **UTC**, and convert to local time only when showing it to a user. Otherwise every record from a different country needs its own conversion. A Unix timestamp is also just an integer — “an hour later” is `+ 3600`.

<p class="wisdom-day">Day 1</p>

## When VS Code does not see installed packages

Mirek admits VS Code is “unpredictable” here. The routine: select the venv interpreter (*Python: Select Interpreter*), then *Python: Restart Language Server* — and if even that does not help, disconnect from the server and reconnect.

<p class="wisdom-day">Day 1</p>

## IntelliJ keyboard shortcuts

Mirek uses IntelliJ keyboard shortcuts in VS Code (formatting code is `Ctrl+Alt+L` for him). If you are coming from PyCharm or IntelliJ, VS Code has the *IntelliJ IDEA Keybindings* extension. The default format shortcut in VS Code is `Shift+Alt+F`.

<p class="wisdom-day">Day 1</p>

## Dynamic typing

In Python, `a = 10`, then `a = "Jano"`, then `a = True` is fine. In C, Java, or C# the compiler would tell you exactly what it thinks of you. Programmers from statically typed languages need a while to get used to it — type hints help them (and the editor), but check nothing at runtime.

<p class="wisdom-day">Day 1</p>

## Close your files

A process has a limit on open files (`ulimit -n`). A workflow that never closes them will eventually crash — hence `with open(...)`.

<p class="wisdom-day">Day 1</p>

## Decorators are everywhere

A decorator is a function that wraps another function. In Python it is a “really beautiful approach”, and whole frameworks are built on it: **click** (`@click.command`), **Flask** and **FastAPI** (`@app.get("/info")` — routing with no magic configuration on the side), and **Airflow** (`@dag`, `@task`).

<p class="wisdom-day">Day 2</p>

## click: a CLI without effort

click is extremely popular because working with it is “good, fast, and easy” — you just **describe** the command's parameters with decorators and the workflow code stays almost unchanged. `--help`, value checks (`click.Choice`), and defaults come for free. Python is a good language for DevOps tools, not only Bash.

<p class="wisdom-day">Day 2</p>

## Organize Imports

Ruff underlines imports that are not sorted (`I001: Import block is un-sorted or un-formatted`). No need to sort them by hand — in *Quick Fix* (`Ctrl+.`) choose **Organize Imports**.

<p class="wisdom-day">Day 2</p>

## Ctrl+/ comments everywhere

Commenting and uncommenting a line or a selection is `Ctrl+/` — a universal shortcut across the big editors (VS Code, IntelliJ…). Unless you have set it up differently.

<p class="wisdom-day">Day 2</p>

## Expose a secret as briefly as possible

If you cannot avoid a secret being visible for a while (e.g. in a process's arguments), keep it **as short as possible**. A process that runs for 30 seconds with a key in its arguments is exposed for 30 seconds to anyone who runs `ps aux`.

<p class="wisdom-day">Day 2</p>

## sys.exit(), not quit()

`quit()` is a helper for the interactive interpreter. In a script, end the program with `sys.exit()` — and in an Airflow task, raise an exception.

<p class="wisdom-day">Day 2</p>

## The DAG function is called main

You can name the function that defines the DAG however you like. Mirek always calls it `main` — “I am not going to invent weather scraper DAG or DAG weather scraper”. The human name belongs in `dag_display_name` anyway.

<p class="wisdom-day">Day 2</p>

## Frequency in the DAG name

From a Kiwi.com talk: they put the run frequency into the DAG name too (e.g. “… 1 hour”) so it is clear straight from the list. Agree on conventions in your team.

<p class="wisdom-day">Day 2</p>

## Do not trim a generated config

Mirek replaced the generated `airflow.cfg` with a short version holding “only what is needed” — and tasks started failing mysteriously. It was missing the random `jwt_secret`. Lesson: keep a generated config whole and change only what you need.

<p class="wisdom-day">Day 2</p>

## pathlib — “you want to use it”

Whenever you do anything with paths — joining them, separating a name from its suffix, finding the parent — use `pathlib.Path`. Forget strings and `os.path`: “It's a really great thing, I have nothing more to add.” See [Project structure](/devops-notes/en/python-advanced/struktura-projektu/#the-pathlib-module).

<p class="wisdom-day">Day 3</p>

## print is DEBUG — and DEBUG never in production

The simplest rule of thumb: anything you would `print()` as a check print is the **DEBUG** level. And never enable that in production — developers print even credentials there, which in production belong to real people.

<p class="wisdom-day">Day 3</p>

## loguru for your own tools

For scripts and CLI tools he recommends the **loguru** library: `from loguru import logger` and you log straight away in a nice coloured format, nothing to configure. A pity it is not compatible with Airflow — stick with `logging` there.

<p class="wisdom-day">Day 3</p>

## sys.exit is a headshot

`sys.exit(1)` in the middle of a program is like a headshot in Quake — the whole game closes and you have to start it again. Report an error in an Airflow task with an **exception**.

<p class="wisdom-day">Day 3</p>

## PyCharm remotely needs a strong machine

PyCharm is still the best environment for Python, but remote development (as in the course) needs a much better machine: it once took 2 GB of disk straight away and kept complaining about low resources. The VS Code server is more modest, although it grows too (1.1 GB on Mirek's machine). Remote development in PyCharm may need a paid licence.
