<KeyPoints>
- Konfigurácia priamo v manifeste skončí v Gite. Ako `.env` súbory v Dockeri, tak tu ConfigMapy a Secrety — oba ukladajú páry **kľúč-hodnota** v **etcd**.
- **ConfigMap** = necitlivé údaje (`describe` ukáže hodnoty). **Secret** = citlivé údaje (`describe` ukáže iba počet bajtov).
- Vytvorenie: `--from-literal KĽÚČ=hodnota` alebo `--from-env-file súbor.env`. Použitie: jeden kľúč cez `valueFrom` (`configMapKeyRef` / `secretKeyRef`), celý objekt cez `envFrom` (`configMapRef` / `secretRef`) — vtedy sa **kľúče musia volať ako premenné aplikácie**.
- `env` má prednosť pred `envFrom`. Hodnoty sa načítajú **pri vytvorení podu** — zmena alebo zmazanie ConfigMapy sa bežiacich podov nedotkne. Pod s odkazom na neexistujúcu ConfigMapu ostane v `CreateContainerConfigError`.
- Secret je iba **base64**, nie šifrovanie: `echo -n 'x' | base64` a späť `base64 --decode`. Na skutočné utajenie sa používajú externé nástroje.
</KeyPoints>

## Prečo

Konfigurácia je zatiaľ súčasťou aplikácie — v manifeste databázy a WordPressu sú premenné prostredia vrátane hesiel. V Dockeri sme to riešili `.env` súbormi, pretože nechceme:

- ručne vypisovať veľa premenných pri každom spustení,
- mať citlivé údaje verejne v **Gite** — každý, kto má prístup k repozitáru, by videl loginy a heslá.

Kubernetes má na to dva objekty:

| | ConfigMap | Secret |
| --- | --- | --- |
| na čo | necitlivá konfigurácia (jednotky, mesto, interval…) | citlivé údaje (heslá, tokeny, API kľúče, certifikáty) |
| `describe` | ukáže kľúče **aj hodnoty** | ukáže iba kľúče a **počet bajtov** |
| uloženie | etcd | etcd, hodnoty v base64 |

Oba sa vytvárajú imperatívne (`kubectl create`) aj deklaratívne (manifest). Pody k nim pristupujú cez **premenné prostredia** alebo ako **súbory vo zväzku**. Keďže sú v etcd, dajú sa zdieľať naprieč klastrom.

Na ukážku slúži aplikácia **weather** — zoznam premenných je na jej stránke na Docker Hube:

- do ConfigMapy: `WEATHER_UNITS`, `WEATHER_QUERY`, `WEATHER_UPDATE_INTERVAL`,
- do Secretu: `WEATHER_TOKEN` (API kľúč OpenWeatherMap).

## ConfigMap

### Vytvorenie

```bash
kubectl create configmap weather \
  --from-literal WEATHER_UNITS=metric \
  --from-literal WEATHER_QUERY=poprad,sk \
  --from-literal WEATHER_UPDATE_INTERVAL=30
```

```bash
kubectl get configmaps                # skrátene cm; get all ich neukáže
# NAME               DATA   AGE
# kube-root-ca.crt   1      9d
# weather            3      5s
kubectl describe configmap weather    # kľúče aj hodnoty
```

`DATA` je počet kľúčov. `kube-root-ca.crt` je certifikát, ktorý Kubernetes pridáva do každého priestoru.

### Jeden kľúč: valueFrom

```yaml
    spec:
      containers:
      - image: bletvaska/weather
        name: weather
        env:
        - name: WEATHER_QUERY          # premenná v kontajneri
          valueFrom:
            configMapKeyRef:
              name: weather            # meno ConfigMapy
              key: WEATHER_QUERY       # kľúč v nej
```

„Vezmi z ConfigMapy `weather` hodnotu kľúča `WEATHER_QUERY` a vlož ju do premennej `WEATHER_QUERY`.“ Meno kľúča a premennej sa tu **nemusí zhodovať** — mapuješ ich ručne. Za každý kľúč sú to však štyri riadky navyše.

### Celá ConfigMapa: envFrom

```yaml
      containers:
      - image: bletvaska/weather
        name: weather
        envFrom:
        - configMapRef:
            name: weather
```

Všetky kľúče ConfigMapy sa stanú premennými prostredia. Tu sa **kľúče musia volať presne ako premenné, ktoré aplikácia očakáva** (aj veľkosť písmen) — inak budú v kontajneri, ale aplikácia ich nepoužije a vezme predvolenú hodnotu (pri weather Košice). `envFrom` je zoznam, takže môžeš načítať viac ConfigMap a Secretov.

### Overenie

```bash
kubectl apply -f weather.yaml
kubectl exec -it deployment/weather -- printenv | grep WEATHER
kubectl logs deployment/weather           # počasie pre Poprad
kubectl describe pod -l app=weather       # sekcia Environment
```

### Priorita

Keď je rovnaká premenná v `env` aj v ConfigMape cez `envFrom`, **vyhrá `env`** — ako v Dockeri, kde ručne zadané `-e` vyhrá nad `--env-file`. Na kurze sme dali do `env` `WEATHER_QUERY=ruzomberok,sk` a v pode bol Ružomberok, nie Poprad. Na poradí kľúčov v manifeste nezáleží. Ak je rovnaký kľúč vo **viacerých** ConfigMapách v `envFrom`, rozhoduje poradie — to je ale chyba v konfigurácii.

### Z .env súboru

```bash title="weather.env"
WEATHER_UNITS=metric
WEATHER_QUERY=poprad,sk
WEATHER_UPDATE_INTERVAL=30
```

```bash
kubectl create configmap weather --from-env-file weather.env
```

Súbor môže mať komentáre a dá sa z neho spraviť šablóna s ukážkovou konfiguráciou, ktorá smie ísť do Gitu.

### Ako manifest

```bash
kubectl create configmap weather --from-env-file weather.env \
  --dry-run=client --output yaml > weather.cm.yaml
kubectl get configmap weather --output yaml        # z existujúcej
```

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: weather
data:
  WEATHER_QUERY: poprad,sk
  WEATHER_UNITS: metric
  WEATHER_UPDATE_INTERVAL: "30"
```

Čísla sú v úvodzovkách — hodnoty v ConfigMape sú vždy reťazce. Do manifestu aplikácie ju daj **pred** deployment, aby pri vytváraní podov existovala.

### Zmazanie a chýbajúca ConfigMapa

```bash
kubectl delete configmap weather
```

Bežiace pody sa **nič** nestane — ConfigMapa sa použije iba pri **vytváraní** podu. Problém nastane, až keď vzniká nový pod (reštart, škálovanie, zmazanie podu):

```bash
kubectl get pods
# weather-…   0/1   CreateContainerConfigError   0   10s
kubectl describe pod -l app=weather
# Warning  Failed  …  Error: configmap "weather" not found
```

Kubernetes sa v pravidelných intervaloch pokúša znova; keď ConfigMapu vytvoríš, pod nabehne. Samotný deployment sa vytvorí aj bez ConfigMapy — jeho definícia je správna, chýba iba zdroj.

### Zmena za behu

Zmena hodnôt v ConfigMape sa prejaví až v **nových** podoch. Bežiace treba reštartovať — zmazať pody, naškálovať deployment na 0 a späť, alebo zmazať a znova aplikovať manifest. Automatický reštart pri zmene ConfigMapy Kubernetes sám nerobí (existujú na to rozšírenia).

:::tip[Reštart deploymentu]
Elegantnejší spôsob, ktorý sa na kurze neukazoval: `kubectl rollout restart deployment/weather` — vymení pody postupne ako pri rolling update.
:::

## Secret

### Vytvorenie

```bash
kubectl create secret generic weather \
  --from-literal WEATHER_TOKEN=<API_KEY>
kubectl create secret generic weather --from-env-file credentials.env
```

`generic` je bežný typ (`Opaque`). Secret vie uložiť aj certifikáty (typ `tls`) alebo prístup do registra.

```bash
kubectl get secrets
# NAME      TYPE     DATA   AGE
# weather   Opaque   1      5s
kubectl describe secret weather
# Data
# ====
# WEATHER_TOKEN:  32 bytes
```

Hodnotu nevidno — len dĺžku.

### Použitie

```yaml
        env:
        - name: WEATHER_TOKEN
          valueFrom:
            secretKeyRef:
              name: weather
              key: WEATHER_TOKEN
```

alebo celý Secret:

```yaml
        envFrom:
        - configMapRef:
            name: weather          # ConfigMap weather
        - secretRef:
            name: weather          # Secret weather — iný typ objektu, rovnaké meno nevadí
```

V kontajneri je hodnota **rozkódovaná** — aplikácia dostane pôvodný token. Po aplikovaní sa v prehliadači konečne zobrazí počasie.

### base64 nie je šifrovanie

```bash
kubectl get secret weather -o yaml
# data:
#   WEATHER_TOKEN: PEFQSV9LRVk+
```

```bash
echo -n 'janosik' | base64              # amFub3Npaw==
echo -n 'amFub3Npaw==' | base64 --decode   # janosik
```

Hodnoty v Secrete sú iba zakódované cez **base64**, ktorý rozkóduje ktokoľvek. Kto môže čítať Secret, vidí aj heslo. Pri ručnom písaní manifestu musíš hodnoty do base64 zakódovať sám (`echo -n`, aby sa nezakódoval aj znak nového riadku).

Na skutočné utajenie sa používajú externé úložiská a rozšírenia — napr. *External Secrets Operator* alebo [gopass](https://github.com/gopasspw/gopass) (v Krew je `kubectl gopass`). Ktoré, rozhoduje tím.

## Jeden objekt pre všetkých?

Na kurze padol návrh: jedna ConfigMapa a jeden Secret `wordpress` pre WordPress aj MariaDB. Funguje to, ale **nie je to bezpečné** — každý kontajner by mal v premenných prístupy aj ku druhej aplikácii, takže stačí hacknúť jednu a máš celú infraštruktúru. Každá aplikácia dostane vlastné objekty.

## Otestuj sa

<Question q="Kedy použiješ ConfigMap a kedy Secret?">
ConfigMap na necitlivú konfiguráciu, Secret na heslá, tokeny a kľúče.
</Question>

<Question q="Aký je rozdiel medzi `valueFrom` a `envFrom`?">
`valueFrom` mapuje jeden kľúč na jednu premennú (mená sa môžu líšiť). `envFrom` načíta všetky kľúče ako premenné — mená kľúčov sa musia zhodovať s premennými aplikácie.
</Question>

<Question q="Premenná je v `env` aj v ConfigMape cez `envFrom`. Ktorá vyhrá?">
Hodnota z `env`.
</Question>

<Question q="Zmazal si ConfigMapu. Čo sa stane s bežiacimi podmi a čo s novými?">
Bežiacim nič — hodnoty dostali pri vytvorení. Nové pody ostanú v `CreateContainerConfigError`, kým ConfigMapu znova nevytvoríš.
</Question>

<Question q="Zmenil si hodnotu v ConfigMape. Kedy ju aplikácia uvidí?">
Až v nových podoch — bežiace treba reštartovať.
</Question>

<Question q="Je Secret v Kubernetes šifrovaný?">
Nie, hodnoty sú iba v base64. Kto môže čítať Secret, prečíta aj hodnotu.
</Question>

<Question q="Prečo nedať prístupy WordPressu aj databázy do jedného Secretu?">
Každý kontajner by videl aj prístupy, ktoré nepotrebuje — kompromitácia jednej aplikácie by prezradila všetky.
</Question>

## Cvičenia

### 12.1 · RustFS s ConfigMapou a Secretom

Manifest pre [RustFS](https://hub.docker.com/r/rustfs/rustfs):

- menný priestor `prod`, obraz `rustfs/rustfs`, jedna inštancia,
- sprístupnené porty 9000 (S3 API) a 9001 (konzola),
- admin `janosik` s heslom `valaska123` (`RUSTFS_ACCESS_KEY`, `RUSTFS_SECRET_KEY`),
- časová zóna `TZ=Europe/Bratislava`,
- pamäť 128Mi až 512Mi, CPU 100m až 500m.

Premenné rieš cez ConfigMapu a Secret.

<p class="practises">Precvičíš: ConfigMap a Secret ako manifest, `envFrom`, viac portov v službe.</p>

<Solution>
```yaml title="rustfs.yaml"
apiVersion: v1
kind: Namespace
metadata:
  name: prod
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: rustfs-config
  namespace: prod
data:
  TZ: Europe/Bratislava
---
apiVersion: v1
kind: Secret
metadata:
  name: rustfs-secret
  namespace: prod
data:
  RUSTFS_ACCESS_KEY: amFub3Npaw==        # janosik
  RUSTFS_SECRET_KEY: dmFsYXNrYTEyMw==    # valaska123
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rustfs
  namespace: prod
  labels:
    app: rustfs
spec:
  replicas: 1
  selector:
    matchLabels:
      app: rustfs
  template:
    metadata:
      labels:
        app: rustfs
    spec:
      containers:
      - image: rustfs/rustfs
        name: rustfs
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 512Mi
        envFrom:
        - configMapRef:
            name: rustfs-config
        - secretRef:
            name: rustfs-secret
---
apiVersion: v1
kind: Service
metadata:
  name: rustfs
  namespace: prod
  labels:
    app: rustfs
spec:
  type: LoadBalancer
  selector:
    app: rustfs
  ports:
  - name: s3
    port: 9000
    protocol: TCP
    targetPort: 9000
  - name: console
    port: 9001
    protocol: TCP
    targetPort: 9001
```

```bash
kubectl apply -f rustfs.yaml
kubectl exec -n prod deployment/rustfs -- date     # čas v strednej Európe (CET/CEST)
# http://<IP>:9001 → janosik / valaska123
```

`TZ` mení iba čas systému v kontajneri (`date`). Čas, ktorý ukazuje webová konzola pri bucketoch, je vec aplikácie. Bez `TZ` by `date` ukázal UTC.
</Solution>

### 12.2 · WordPress — security first

Uprav manifest [WordPressu](/devops-notes/kubernetes/wordpress/) tak, aby žiadne heslo nebolo priamo v deploymente. Každá aplikácia dostane vlastnú ConfigMapu a vlastný Secret.

<p class="practises">Precvičíš: rozdelenie konfigurácie, base64, `envFrom`.</p>

<Solution>
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: wordpress
  namespace: wordpress
data:
  WORDPRESS_DB_HOST: db:3306
  WORDPRESS_DB_NAME: wordpress
---
apiVersion: v1
kind: Secret
metadata:
  name: wordpress
  namespace: wordpress
data:
  WORDPRESS_DB_USER: d3B1c2Vy              # wpuser
  WORDPRESS_DB_PASSWORD: ZW5kMzIx          # end321
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: mariadb
  namespace: wordpress
data:
  MARIADB_DATABASE: wordpress
---
apiVersion: v1
kind: Secret
metadata:
  name: mariadb
  namespace: wordpress
data:
  MARIADB_ROOT_PASSWORD: dG9wLnNlY3JldA==  # top.secret
  MARIADB_USER: d3B1c2Vy
  MARIADB_PASSWORD: ZW5kMzIx
```

V deploymentoch nahraď `env` za:

```yaml
        envFrom:                 # db
        - configMapRef:
            name: mariadb
        - secretRef:
            name: mariadb
```

```yaml
        envFrom:                 # app
        - configMapRef:
            name: wordpress
        - secretRef:
            name: wordpress
```

Na kurze sa raz pomýlilo meno a WordPress dostal ConfigMapu a Secret `mariadb` — over si to cez `kubectl exec … -- printenv`.
</Solution>
