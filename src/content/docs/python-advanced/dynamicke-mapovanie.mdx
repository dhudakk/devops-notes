<KeyPoints>
- **Dynamic Task Mapping** vytvorí **za behu** jednu inštanciu tasku pre každú položku zoznamu. Nemusíš robiť 10 (alebo 800) rovnakých DAG-ov, ktoré sa líšia iba parametrom.
- Parameter DAG-u ako zoznam: `@dag(params={"query": Param(default=[...], type="array", title=..., description=...)})` — vo formulári Trigger je to pole „jedna položka na riadok“.
- Variable s mestami (jedno na riadok) je reťazec — na zoznam ho zmeníš cez `.split()`.
- Parametre behu sú v **kontexte**, ktorý dostaneš iba v tasku: `get_current_context()["params"]["query"]`.
- `.expand(query=locations)` — jedna inštancia pre každú položku; `.partial(units="metric")` — rovnaká hodnota pre všetky inštancie.
- Mapuj **celú skupinu**: `tg_weather_ingestion.expand(query=locations)`. Chyba jedného mesta potom zastaví iba jeho vetvu; s `AirflowSkipException` beh dokonca skončí úspešne.
</KeyPoints>

## Problém

DAG sťahuje počasie pre jedno mesto. Chceme ich **viac** — a pre každé mesto zvlášť stiahnuť, overiť, spracovať a publikovať. Robiť pre každé mesto vlastný DAG nedáva zmysel: na univerzite, kde Mirek učí, sa Airflow chystá na hodnotenie študentských zadaní — DAG pre jedného študenta je jednoduchý, ale študentov je 800+.

Riešením je **Dynamic Task Mapping**: DAG ostane jeden a Airflow za behu vytvorí toľko inštancií taskov, koľko je položiek v zozname.

Treba vyriešiť dve veci:

1. ako zadať **zoznam** miest — v Variable aj ručne pri spustení,
2. ako tasku dávať mestá **po jednom**.

## Parameter DAG-u: Param

Doteraz bol `query` obyčajný reťazec (`query: str = …`). Vo formulári Trigger je to jednoriadkové pole — Enter tam nenapíšeš. Typ **`Param`** z `airflow.sdk` opíše parameter podrobnejšie:

```python
from airflow.sdk import Param

Param(
    default=[],
    type="array",                 # Airflow types, as strings — not Python types
    title="Locations",
    description="List of locations. One location per line.",
)
```

| Vlastnosť | Význam |
| --- | --- |
| `type` | typ hodnoty ako reťazec: `"string"`, `"integer"`, `"number"`, `"boolean"`, `"array"`, `"object"` (ako v [JSON Schema](/devops-notes/python-advanced/validacia-dat/)) |
| `default` | predvolená hodnota |
| `title` | nadpis poľa vo formulári Trigger |
| `description` | popis pod poľom |

### Kam s ním: `params=` v dekorátore

Lektor ho najprv dal ako predvolenú hodnotu parametra funkcie: `def main(query=Param(...))`. Ruff to podčiarkol (*Do not perform function call `Param` in argument defaults* — pravidlo B008) a pri viacerých parametroch by bola hlavička funkcie obrovská — každý má 5 riadkov. Preto patria do slovníka **`params`** v `@dag`:

```python
@dag(
    "weather_scraper",
    ...,
    params={
        "query": Param(
            default=Variable.get("weather_city", default="kosice,sk").split(),
            type="array",
            title="Locations",
            description="List of locations. One location per line.",
        ),
    },
)
def main():
    ...
```

### Mestá z Variable: `.split()`

Variable `weather_city` má mestá na samostatných riadkoch — je to **reťazec** s `\n`. Keď ho dáš ako `default` parametra typu `array`, Airflow ho odmietne:

```text
ParamValidationError: 'kosice,sk\npresov,sk' is not of type 'array'
```

Reťazec treba rozdeliť na zoznam metódou **`split()`**. Bez argumentu delí podľa **bielych znakov** (medzera, tabulátor, nový riadok); s argumentom podľa zadaného oddeľovača (`"a,b".split(",")`):

```python
>>> "ruzomberok,sk\nkosice,sk\npresov,sk".split()
['ruzomberok,sk', 'kosice,sk', 'presov,sk']
```

Vo formulári Trigger je potom pole so zoznamom miest z Variable — pri plánovaných behoch sa použije tak, ako je; pri ručnom spustení ho môžeš prepísať (napr. len pre jedno mesto na test).

:::tip[Keď vo formulári vidíš iba prvé mesto]
U účastníka sa vo formulári ukazovalo iba prvé mesto. Kód aj Variable boli v poriadku — v Airflow viseli staré nedokončené behy. Pomohol `sudo systemctl restart airflow` a obnovenie stránky.
:::

## Kontext behu

Ako sa k parametru dostať? Funkcia `main()` sa vykoná pri **parsovaní** DAG-u — vtedy ešte žiadny beh neexistuje. Hodnoty patria konkrétnemu behu a sú v **kontexte**.

**Kontext** je pojem, ktorý stretneš v aplikáciách všade: niečo ako globálne dáta dostupné z každého miesta aplikácie. V Airflow má každý beh DAG-u (a každý task) svoj kontext — kedy beh vznikol, aký DAG, aké parametre, inštancia tasku… Získaš ho **iba v tasku** funkciou `get_current_context()`:

```python
from pprint import pprint

from airflow.sdk import get_current_context, task


@task(task_display_name="Get Locations")
def get_locations() -> list[str]:
    context = get_current_context()
    pprint(context)                       # let us see what is inside
    return context["params"]["query"]
```

Kontext je slovník (v Airflow 3.3 napr. kľúče `dag`, `dag_run`, `run_id`, `logical_date`, `params`, `task`, `ti` / `task_instance`, `triggering_asset_events`…). `print()` ho vypíše do jedného dlhého riadku, `pprint` (*pretty print*) prehľadne. `params` je slovník v slovníku, preto `context["params"]["query"]`.

:::caution[`-> dict` nie je len poznámka]
Lektor najprv napísal `def get_locations() -> dict:` a task zlyhal: *Returned output was type &lt;class 'list'&gt; expected dictionary for multiple_outputs*. Keď je návratový typ tasku `dict`, Airflow z neho odvodí `multiple_outputs=True` — rozloží slovník na samostatné XCom hodnoty a slovník aj vyžaduje. Task vracia zoznam, takže správne je `-> list[str]`.
:::

## .expand() a .partial()

Keď výsledok `get_locations()` (zoznam) dáš priamo do `scrape_data(locations)`, task sa nezrúti — ale spustí sa **raz** pre celý zoznam. httpx z neho spraví opakovaný parameter `?q=ruzomberok,sk&q=kosice,sk&…` a OpenWeatherMap vezme iba prvé mesto. My chceme jednu inštanciu pre každé mesto.

| Metóda | Význam |
| --- | --- |
| `.expand(arg=zoznam)` | argument, podľa ktorého sa task rozmnoží — do `arg` sa postupne dosadí každá položka zoznamu |
| `.partial(arg=hodnota)` | argumenty **rovnaké** pre všetky inštancie |

```python
locations = get_locations()
data = scrape_data.expand(query=locations)   # query: str ← one city at a time
valid_data = validate_data.expand(payload=data)
```

- `query` je reťazec (jedno mesto), `locations` je zoznam. `expand` „rozbalí“ zoznam a pre každú položku spustí jednu inštanciu so `query` = to mesto.
- Výsledok namapovaného tasku je opäť zoznam, takže aj ďalší task sa mapuje cez `.expand(...)`.
- V grafe má namapovaný task za názvom **hranaté zátvorky** s počtom inštancií. V záložke *Mapped Tasks* sú inštancie očíslované (*map index* 0, 1, 2…) v poradí zoznamu. Ktoré mesto je ktoré, nájdeš v detaile inštancie v *Rendered Template*.

**`.partial()`** — keby `scrape_data` mal aj parameter `units`, rovnaký pre všetky mestá:

```python
scrape_data.partial(units="metric").expand(query=locations)
# scrape_data(query="kosice,sk", units="metric"), scrape_data(query="presov,sk", units="metric"), …
```

## Keď jedno mesto zlyhá

Lektor do zoznamu pridal neexistujúce mesto `xxxx`. OpenWeatherMap vrátil 404, jeho `scrape_data` zlyhal — a **všetky** inštancie `validate_data` a ďalšie boli `upstream_failed`. Ani mestá, ktoré sa stiahli v poriadku, sa nespracovali.

Prečo: pri reťazení `scrape_data.expand(...)` → `validate_data.expand(...)` závisí namapovaný `validate_data` od **celého** namapovaného `scrape_data`. Zlyhá jedna inštancia → zlyhá závislosť pre všetky.

### Riešenie: mapovaná skupina taskov

Namiesto jednotlivých taskov namapuj **celú skupinu** — každé mesto dostane vlastnú vetvu `scrape → validate → process → publish`:

```python
@task_group(group_display_name="Weather Ingestion")
def tg_weather_ingestion(query: str):
    data = scrape_data(query)          # inside the group: ordinary calls, no expand
    valid_data = validate_data(data)
    line = process_data(valid_data)
    publish_data(line)


@dag(...)
def main():
    locations = tg_healthcheck() >> get_locations()
    tg_weather_ingestion.expand(query=locations)
```

<Pipeline steps={[{ group: 'Healthcheck', steps: ['ping', 'openweathermap', 'rustfs'] }, 'get_locations', { group: 'Weather Ingestion [N]', steps: ['scrape → validate → process → publish'] }]} caption="Skupina sa namapuje N-krát — jedna vetva pre každé mesto." />

Overené na Airflow 3.3.2 so zoznamom `kosice, xxx, presov`:

| Variant | Spracované mestá | Beh DAG-u |
| --- | --- | --- |
| `scrape.expand` → `validate.expand` → `publish.expand` | **žiadne** | `failed` |
| `tg.expand(...)`, neznáme mesto → `AirflowFailException` | Košice, Prešov | `failed` |
| `tg.expand(...)`, neznáme mesto → **`AirflowSkipException`** | Košice, Prešov | `success` |

### Preskočenie: AirflowSkipException

`AirflowFailException` je univerzálne „zrúbalo sa to“. Špeciálne výnimky majú špeciálne správanie: **`AirflowSkipException`** označí task ako **`skipped`** (ružová) a tasky za ním vo vetve sa tiež preskočia. Lektor ju používa pri hodnotení zadaní — študent, ktorý neurobil zmenu v kóde, sa preskočí. Z 800 študentov tak ostane 200 so zmenou, z nich niektorým zlyhá kompilácia, a hodnotia sa iba zvyšní.

```python
from airflow.sdk.exceptions import AirflowSkipException

if response.status_code == HTTPStatus.NOT_FOUND:
    logger.warning("Unknown city %s, skipping", query)
    raise AirflowSkipException(f"City {query} not found.")
```

Na kurze to lektor nestihol rozchodiť (skúšal aj `trigger_rule="all_done"`); s mapovanou skupinou to funguje, ako je v tabuľke vyššie. Či je neznáme mesto chyba (`failed`) alebo len „nie je čo robiť“ (`skipped`), je rozhodnutie návrhu.

:::caution[Viac inštancií zapisuje do jedného súboru]
Všetky vetvy pripisujú do toho istého `dataset.csv` v S3 („stiahni → pripíš → nahraj“). Keby dve inštancie `publish_data` bežali naraz, jedna by prepísala zápis druhej. Na kurze to nevadilo (nízky `parallelism`), ale istejšie je obmedziť súbeh: `@task(..., max_active_tis_per_dagrun=1)` — v rámci jedného behu beží najviac jedna inštancia `publish_data` naraz. Alternatíva je vlastný súbor pre každé mesto (`kosice-sk.csv`).
:::

Ďalší dôsledok: `publish_data` má `outlets=[WEATHER_DATA]` a teraz beží raz za každé mesto — **každá** úspešná inštancia vytvorí udalosť assetu. V teste sa `report_builder` spustil dvakrát pri behu s dvoma mestami.

## Celý DAG

Výsledný `weather_scraper.py` (s notifikáciami z ďalšej kapitoly) je v kapitole [Polnočný report](/devops-notes/python-advanced/polnocny-report/#celý-projekt-po-5-dni). Podstatné časti:

```python
@task(task_display_name="Get Locations")
def get_locations() -> list[str]:
    """Cities for this run — from the Trigger form, or the default from the Variable."""
    context = get_current_context()
    return context["params"]["query"]


@task_group(
    group_display_name="Weather Ingestion",
    tooltip="Retrieve, process and upload weather info.",
)
def tg_weather_ingestion(query: str):
    data = scrape_data(query)
    valid_data = validate_data(data)
    notify(valid_data)
    line = process_data(valid_data)
    publish_data(line)


@dag(
    "weather_scraper",
    ...,
    params={
        "query": Param(
            default=Variable.get("weather_city", default="kosice,sk").split(),
            type="array",
            title="Locations",
            description="List of locations. One location per line.",
        ),
    },
)
def main():
    locations = tg_healthcheck() >> get_locations()
    tg_weather_ingestion.expand(query=locations)
```

## Otestuj sa

<Question q="Čo je Dynamic Task Mapping a aký problém rieši?">
Za behu vytvorí jednu inštanciu tasku (alebo skupiny) pre každú položku zoznamu. Nemusíš robiť samostatný DAG pre každé mesto či študenta — DAG je jeden a mení sa iba vstup.
</Question>

<Question q='Prečo zlyhá `Param` typu `"array"` s predvolenou hodnotou `Variable.get("weather_city")` a ako to opraviť?'>
Variable je reťazec s mestami na riadkoch, nie zoznam: *is not of type 'array'*. Treba `Variable.get(...).split()`.
</Question>

<Question q="Prečo patria parametre DAG-u do `params=` v `@dag` a nie do hlavičky `main()`?">
Volanie funkcie v predvolenej hodnote parametra je zlý zvyk (Ruff B008) a pri viacerých parametroch by bola hlavička obrovská. V `params` je slovník — prehľadný a v Airflow štandardný.
</Question>

<Question q="Ako sa v tasku dostaneš k parametru `query` z formulára Trigger?">
`get_current_context()["params"]["query"]` — kontext je dostupný iba počas behu tasku.
</Question>

<Question q="Prečo task s `-> dict`, ktorý vracia zoznam, zlyhá?">
Pri návratovom type `dict` Airflow nastaví `multiple_outputs=True` a očakáva slovník.
</Question>

<Question q="Aký je rozdiel medzi `.expand()` a `.partial()`?">
`.expand()` dosadí do argumentu postupne každú položku zoznamu (jedna inštancia na položku). `.partial()` nastaví argument rovnaký pre všetky inštancie.
</Question>

<Question q="Prečo pri reťazení `scrape.expand()` → `validate.expand()` jedno zlé mesto zastaví všetky?">
Namapovaný `validate` závisí od celého namapovaného `scrape`; keď jedna inštancia zlyhá, všetky inštancie `validate` sú `upstream_failed`. Riešením je namapovať celú skupinu (`tg.expand(...)`) — každé mesto má vlastnú vetvu.
</Question>

<Question q="Aký je rozdiel medzi `AirflowFailException` a `AirflowSkipException` v mapovanej skupine?">
Pri `AirflowFailException` sa ostatné mestá spracujú, ale beh skončí `failed`. Pri `AirflowSkipException` sa vetva označí `skipped`, ostatné mestá sa spracujú a beh skončí `success`.
</Question>

## Cvičenia

### 19.1 · Mestá bez duplicít

Uprav `get_locations()`, aby odstránil medzery okolo názvov, zmenil ich na malé písmená a vyradil prázdne položky a duplicity (poradie zachovaj).

<Solution>
```python
@task(task_display_name="Get Locations")
def get_locations() -> list[str]:
    locations = get_current_context()["params"]["query"]
    cleaned = (location.strip().lower() for location in locations)
    return list(dict.fromkeys(location for location in cleaned if location))
```

`dict.fromkeys()` zachová poradie prvého výskytu a duplicity zahodí (kľúče slovníka sú jedinečné).
</Solution>

### 19.2 · Neznáme mesto preskoč

Uprav `scrape_data`, aby pri 404 zalogoval WARNING a vetvu daného mesta **preskočil** (beh má skončiť úspešne); pri ostatných chybách nech zlyhá.

<Solution>
```python
from airflow.sdk.exceptions import AirflowFailException, AirflowSkipException


@task(task_display_name="Scrape Data")
def scrape_data(query: str) -> dict:
    ...
    response = httpx.get(url, params=params, timeout=10)
    if response.status_code == HTTPStatus.NOT_FOUND:
        logger.warning("Unknown city %s, skipping", query)
        raise AirflowSkipException(f"City {query} not found.")
    if response.status_code != HTTPStatus.OK:
        raise AirflowFailException(f"Cannot get weather for {query}: {response.text}")
    return response.json()
```

Funguje to vďaka mapovanej skupine: preskočí sa iba vetva neznámeho mesta.
</Solution>
